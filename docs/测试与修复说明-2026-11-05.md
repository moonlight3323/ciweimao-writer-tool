## 二、逐条说明

### B1（致命）插件脚本被主界面的 CSP 拦掉，插件一直白屏

**现象**
插件中心里点任何插件的「打开」，右侧宿主区一片空白。界面不报错，只有开发者工具里能看到
`Loading the script 'data:text/javascript;base64,...' violates ... "script-src 'self'"`。

**原因**
插件是「把 `page.html` + `style.css` + `main.js` 合成一个 `data:` 文档，塞进 `sandbox="allow-scripts"` 的 iframe」。
而 **`data:` / `blob:` 这类本地文档会继承父页面的 CSP**。主界面 `index.html` 里写的是
`script-src 'self'`，于是注入的桥（`PluginAPI`）和插件自己的 `main.js` 全被拒绝执行 —— 页面骨架在，脚本一个都没跑，看起来就是白屏。

**修复**
主界面 CSP 的 `script-src` 加上 `data:`：

```
script-src 'self' data:
```

其余限制一条没松（父页面仍是 `default-src 'self'`；插件文档自己那份 CSP 仍是 `default-src 'none'`，
插件依旧不能联网、不能加载外链、拿不到主界面）。

**验证**
`tools/ui-plugin-sample.js`：把示例插件塞进真沙箱打开，以「主进程收到了 `storage.get` 调用」作为
`main.js` 确实执行了的证据（打桩可以让 DOM 看起来正常，但伪造不了一次真的跨进程请求）。

**留给以后的话**
CSP 那一行旁边写了注释，说明这半句不能删。**这是最容易被「顺手收紧安全策略」的人改回去的地方。**

### B2（致命）Writer 的插件接口作用域写错，读正文与读统计一直抛异常

**现象**
插件调 `PluginAPI.editor.getContext()` 或 `PluginAPI.stats.get()`，必然以
`currentBook is not defined` 失败。

**原因**
`src/renderer/writer.js` 里，`pluginContext()` 和 `pluginStats()` 写在对象字面量 `const api = { ... }` 内，
却直接调用了 `currentBook()` / `currentChapter()`。这两个是 **`api` 上的方法**，不是自由函数，
在对象里裸调就是 `ReferenceError`。

同一个对象里的 `pluginSetContent()` 写的是 `api.replaceText(...)` —— 正确写法就在隔壁，但没人跑过一次。

**修复**
改为 `api.currentBook()` / `api.currentChapter()`（4 处）。

**验证**
`ui-plugin-sample.js` 里直接断言 `Writer.pluginStats()` 返回结构里有 `totalWords`/`todayWords`、
`Writer.pluginContext()` 在没打开章节时返回 `null` 而不是抛错。

### B3（严重）处理失败的提示被静默吞掉

**现象**
点「一键处理」失败时（典型：词被换行拆成两段，页面上替换不到；或编辑器没响应），
小窗一动不动，作者会以为已经改好了。

**原因**
主窗口 `publish.js` 的 `notice()` 会推一份带 `notice:{kind,text}` 的状态给侧栏，
但侧栏 `side.js` **没有渲染 `notice` 的分支** —— 消息收下了、丢掉了。
而原本兜底的 toast 又会被原生页面视图盖住（后台页面层级在网页 DOM 之上），等于彻底没反馈。

**修复**
- 侧栏加提示条 `#sideNotice`：错误红底、提示黄底，可手动关闭；
- `notice` 改为「一次性推送」（`transient`），**不写进 `lastPayload`** —— 否则关掉窗口再打开还会看到上一条旧错误。

**验证**
`ui-side.js` 断言提示条可见、文案正确、可关闭；`ui-writer.js` 断言失败路径确实把原因推给了侧栏，
且 `state.lastPayload` 里没有残留 `notice`。

### B4（严重）推一条提示，会把已选方案重置

**现象**
作者把某个词改成「近义」，随后界面提示一条错误，回头一看选项全变回默认了。

**原因**
提示走的也是「整份状态推送」，而 `renderBad()` 收到状态就无条件重建整个词表 DOM —— 重建即重置。

**修复**
给词表加内容指纹 `itemsKey()`（`词|是否命中|出现次数` 拼接）。词表没变时只刷新顶部说明文字，
不动列表和已选项：提示归提示，选择归选择。

**验证**
`ui-side.js`：先把命中词切成「近义」→ 推一条同内容的错误提示 → 断言该词仍选中「近义」。

---

### B5（严重）主窗口最小化时打开侧栏，窗口跑到屏幕左上角

**现象**
主窗口处于最小化状态时打开侧栏，侧栏出现在屏幕左上角、**高度只有 280px**。

**原因**
Windows 上窗口最小化后 `getContentBounds()` 返回 `x = -32000, width = 0, height = 0`。
`place()` 拿这组数算位置和高度，`Math.max(280, ...)` 又把高度兜到最小值 —— 结果就是左上角一个 372×280 的小条。

**修复**
两道防线：
1. 矩形无效（宽或高 < 100，或 `x < -20000`）直接跳过摆位，保持原位；
2. 主窗口最小化时不显示侧栏，`open()` 返回 `{ ok:true, deferred:true }`，等主窗口 `restore` 再出现。

**验证**
`probe-app-pubside.js`：在「环境强制最小化」的分支里断言返回 `deferred` 且没有被摆到错误位置。

### B6（一般）手动摆好的位置会被拽回去

**现象**
侧栏拖到副屏（或主窗口外任意位置），主窗口最小化再还原，它又被拉回主窗口右边。

**原因**
`restore` 事件走的是 `openSide(lastState)`，而 `openSide` 里会 `manual = false`（重置为「自动跟随」）。

**修复**
`openSide(state, { keepPosition: true })`：系统触发的显示保留作者摆放的位置，只有点顶栏重新打开才回默认位置。

**验证**
`probe-pubside.js`：手动挪动 → 移动主窗口（不被拽回）→ 最小化/还原（位置保持）。

---

### B7（一般）侧栏首次打开偶发不可见

**现象**
偶尔打开侧栏没有任何窗口出现，操作后（比如切页面）才冒出来。

**原因**
`showInactive()` 在页面尚未加载完成时偶发不生效，窗口停在创建时的 `show:false`。
另外首次 `open` 时的状态推送也发早了（页面还没加载完，消息被丢弃，表现为小窗是空的默认文案）。

**修复**
- `did-finish-load` 里补发一次状态；
- `showInactive()` 之后 320ms 兜底检查，仍不可见就改调 `show()`。

**验证**
连续 3 次运行端到端探针稳定通过（此前约一半概率红）。

---

### B8（一般）切页面时侧栏还浮着

**现象**
在码字台打开侧栏后切到「概览」「设置」，小窗还盖在内容上。

**修复**
`app.js` 的 `setActiveView()` 发出 `view-changed` 事件；`publish.js` 离开码字台时收起（记住 `sideParked`），
回到码字台自动放出来 —— 内容不丢，只是不在不相干的页面碍眼。

**验证**
`ui-writer.js`：切到 overview 断言侧栏隐藏、切回 writer 断言恢复且内容还在。

---

### B9（一般）「一键处理」可以连点

**现象**
点下去到处理完成有 0.5~1 秒间隙，期间按钮仍可点，可能触发两次改正文。

**修复**
点击立即进入忙碌态：按钮置灰、文案变「正在处理…」；失败收到提示后自动恢复，成功则界面已切到待发布态。

**验证**
`ui-side.js` 断言点击后按钮 `disabled` 且文案含「正在处理」。

## 三、测试与环境问题（不算产品 bug）

### T1　一个陈旧用例一直红着，误导排查
`tools/test-exec-ui.js` 点的是 `#btnRandomComment` 等按钮，而「执行台」独立页在 **v0.6.0** 就并进了「评论审查」，
这些元素早已不存在，跑起来必然 `Script failed to execute`。

**处理**：改名 `_stale-test-exec-ui.js`，文件头写明废弃原因与替代用例（`ui-review-check.js`）。
`_` 前缀 = 不在默认回归清单里。

### T2　打包被宿主的 safe-delete 钩子拦住
`build-portable.js` 里的 `fs.rmSync` 被 `NODE_OPTIONS` 注入的 `genie-safe-delete.cjs` 拦截，报 `trash-failed`。

**处理**：打包命令前加 `env -u NODE_OPTIONS`（`build-portable` / `finish-portable` / `build-devpack` / `_smoke-packaged` 同理），已写进交接文档。

### T3　窗口位置类断言在自动化环境里时红时绿
本机会话会把窗口强制最小化，`getContentBounds()` 随之变成无效值，位置断言就不稳定。

**处理**：探针先 `restore() + show()`；若仍被最小化，就把「可见」这类断言标 `SKIP` 并打印原因
（不是产品缺陷），其余（摆位、渲染、命令链路）照测。

## 四、为什么之前没测出来

这三条比 bug 本身更值得记：

1. **只验属性，不等于验行为。**
   插件中心此前只断言了 `iframe` 的 `sandbox` 属性值，没人真的打开过一个插件。
   属性对、但脚本被 CSP 拦着 —— 这种「静态检查通过、运行时全废」的洞，只有真跑一次才现形。

2. **测试桩把失败路径做成了「不会失败」。**
   侧栏的错误提示在桩里从来没被触发过，所以 B3 一直藏着。**失败路径必须有人造一次失败去点。**

3. **非常规状态没人走。**
   B5（最小化）、B6（拖到副屏）都发生在「不是正常操作路径」的状态里。
   功能测试默认窗口是正常显示且在主屏，这类 bug 永远不会自己冒出来。

## 六、还有哪些没验过（不要当成已验证）

1. **真实后台页面的发布闭环**：删除式修改（`to` 为空）在真 KindEditor 上没跑过，
   要看删完分段/图片还在不在、会不会留空 `<p></p>`。
2. **`hint_words` 真实格式**：解析器兼容多种格式，但没对照过站点的真实响应；
   每次校验的原文会写进 `data/publish-debug.json`，第一次真发时照它校准。
3. **插件生态**：只跑过自己写的示例，第三方插件的行为没样本。
